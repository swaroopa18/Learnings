## Short Notes: Define Success Tests

- Purpose: Verify that the API works correctly under valid conditions.
- Valid request: Provide correct input data and all required fields.
- Expected status: Define the expected success status code or condition.
- Expected response: Specify the expected response body and required output fields.
- Schema validation: Check that output values follow the required format and allowed types.
- State behavior: Verify conversation or system state changes, if applicable.
- Tool handling: Ensure tool results are processed correctly, if applicable.
- Next step: Define what the client or downstream system should do with the response.

### Example: Support Summary API

- Request: Valid `account_id`, `issue_text`, and `approved_context_ids`.
- Expected result: Response contains `issue_summary`, `urgency`, `recommended_next_action`, `source_ids`, `confidence_note`, `needs_human_review`, and `review_reason`.
- Schema: `urgency` must be low, medium, or high; `needs_human_review` must be true or false.
- What it proves: The API returns all required fields for a valid request.

### Important Points

- Write tests clearly so they can be automated later.
- Success tests do not verify error handling, permissions, performance, or production readiness.
- Include separate tests for failures, security, and other requirements.

## Define Error and Failure Tests

- Purpose: Check whether the API behaves safely and predictably when requests fail.
- Missing fields: Test requests without required fields.
- Authentication: Verify that invalid credentials are rejected.
- Authorization: Ensure authenticated users cannot access unauthorized data.
- Invalid inputs: Test incorrect data types, invalid values, and unsupported inputs.
- Missing context: Check behavior when required information or sources are unavailable.
- Timeouts and retries: Verify how the API handles delays and temporary failures.
- Structured output: Test responses that do not match the required schema.
- State mismatch: Check incorrect conversation or system state.
- Tool failures: Verify handling of unavailable tools or tool errors.
- Approval required: Ensure actions requiring approval are not performed without it.
- Out-of-scope requests: Check that unsupported requests are handled appropriately.

### Example: Missing Required Field

- Request: `issue_text` is present, but `account_id` is missing.
- Expected result: The API returns a defined error or structured failure response.
- What it proves: Required fields are validated before processing.

### Example: Unauthorized Access

- Request: An authenticated user tries to access an account without permission.
- Expected result: Access is denied, and protected account data is not returned.
- What it proves: Authentication and authorization are handled separately.

Key takeaway: Success tests verify normal behavior, while error and failure tests verify safe handling of invalid requests, access restrictions, and system failures.

## Test State, Streaming, Async, Steering, Retry, and Idempotency

- Stateless interactions: Verify each request contains enough context to work independently without relying on hidden previous conversations.
- Stateful interactions: Check whether conversation context is retained correctly and handle missing, expired, or mismatched conversation references.
- Streaming: Verify how partial responses, failures, and final structured-output validation are handled.
- Async tool use: Test valid results, unavailable tools, incorrect `call_id`, and timeouts. Never attach results to the wrong call or treat pending work as complete.
- Steering: Verify that accepted updates affect the next response. Check tool-result and approval requirements, and review earlier actions that conflict with new instructions.
- Retry: Test repeated requests after timeouts to ensure work is handled correctly.
- Idempotency: Ensure retrying the same request does not create duplicate records, messages, or customer-visible actions.

### Examples

1\. State mismatch test

- Request: A follow-up question references the wrong conversation.
- Expected result: The API asks for clarification or returns a structured state-mismatch error.
- Proves: Incorrect context is handled safely.

2\. Retry test

- Request: The client resends a request after a timeout.
- Expected result: No duplicate records or customer-visible actions are created.
- Proves: Retry and idempotency expectations are defined.

Key takeaway: Test these behaviors at the API contract level to identify hidden assumptions about context, partial responses, asynchronous tools, steering, retries, and duplicate actions.

## Capture Verification Evidence

Purpose: Record test results clearly so technical stakeholders can review and verify them.

### What to Capture

- Test description: Command, request, or test performed.
- Expected response: The result the API should return.
- Actual response: The result actually received.
- Test status: Pass, fail, or needs review.
- What it proves: Which contract requirement was verified.
- What it does not prove: Any untested behavior or limitation.
- Open questions: Pending validations, responsible owners, or further testing needed.

### Example: Valid Support Summary Request

- Request: Required fields `account_id`, `issue_text`, and `approved_context_ids` are present.
- Expected response: All required summary fields are returned in the correct structure.
- Actual response: Illustrative response contains the required fields.
- Result: Pass (only if verified against an actual test).
- Proves: Basic success response meets the contract.
- Does not prove: Permissions, source availability, scalability, or production readiness.
- Open question: Validate the exact structured-output requirements.

### Key Takeaways

- Record actual results; never present illustrative results as real test evidence.
- Keep evidence clear, accurate, and reviewable.
- Use findings to identify gaps and plan further validation.
- Verification evidence supports technical review and dashboard reporting, but does not alone prove production readiness.

## From Contract to Verification Evidence

API purpose: Generate support summaries for an internal dashboard.

### Required Inputs

- `account_id`
- `issue_text`
- `approved_context_ids`

### Required Outputs

- `issue_summary`
- `urgency`
- `recommended_next_action`
- `source_ids`
- `confidence_note`
- `needs_human_review`
- `review_reason`

### Essential Verification Tests

1. Success test: Valid request returns all required fields in the correct structure.
2. Missing-field test: Missing `account_id` returns a defined error.
3. Authentication test: Invalid credentials result in a safe authentication error.
4. Authorization test: Unauthorized callers cannot access account details.
5. Unsupported-context test: Missing or unavailable evidence does not lead to invented claims; the API returns a controlled failure or flags human review.
6. Structured-output test: Returned results follow the schema, while refusals or incomplete outputs are handled safely.
7. Review-trigger test: When review is required, `needs_human_review` is `true` and `review_reason` explains why.

### Key Takeaway

A weak plan tests only successful requests. A strong plan verifies the entire API contract, including failures, security, context, and output structure.

The evidence helps technical stakeholders decide whether the API is ready for implementation, needs fixes, or requires deeper review.


## Recommended Exercise: Turn a Contract into Verification Tests

Purpose: Create a verification plan for the support-summary API.

### 1. Success Test

- Request: Valid `account_id`, `issue_text`, and `approved_context_ids`.
- Expected result: All seven required output fields are returned in the correct structure.
- Proves: The API meets basic success requirements.

### 2. Error Test

- Request: Omit `account_id`.
- Expected result: A defined missing-field error is returned.
- Proves: Required fields are validated.

### 3. Structured-Output Test

- Request: Submit valid input with approved context.
- Expected result: Output follows the schema; `urgency` is `low`, `medium`, or `high`, and `needs_human_review` is a Boolean.
- Proves: The response follows the required format.

### 4. State-Behavior Test

- Request: Submit a follow-up using an expired or mismatched conversation reference.
- Expected result: The API returns a state-mismatch error or asks for clarification instead of using incorrect context.
- Proves: Conversation state is handled safely.

### 5. Optional Retry Test

- Request: Resend the same request after a timeout.
- Expected result: No duplicate dashboard entries or customer-visible actions are created.
- Proves: Retry and idempotency expectations are defined.

### 6. Verification Evidence

For every test, record:

- Test request and description
- Expected response
- Actual response
- Result: Pass, Fail, or Needs Review
- What it proves and does not prove
- Open questions and validation owners

Reflection: A planned test is not a pass. Mark tests as unexecuted until actual responses have been captured and checked against the contract.
